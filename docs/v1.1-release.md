## 1. Release Overview

Kairo V1.1 is the major feature and reliability release following the V1.0 convergence. While V1.0 unified the core runtime, multi-agent supervisor, tool execution loop, and security center, **V1.1 elevates Kairo into a true autonomous personal assistant with situational awareness and unified command.**

Key advancements in V1.1 include:
1. **Personal Context Engine**: Intelligently understands what the user is working on, resolves project affinity, tracks recent working history, and retrieves semantically relevant long-term memories with explainable provenance.
2. **Project Workspaces**: First-class project workspaces linking repositories, workflows, and conversations with strict multi-tenant authorization boundaries.
3. **Unified Command Center UI**: Modern, single-window operating interface unifying Chat, Context, Projects, Automations, Activity Logs, Security, Memory, and System Status with keyboard-driven Command Palette (`Ctrl+K`).
4. **Hardened Multi-Tenant Security & Stress Resilience**: Complete database migration coverage (23 tables), eliminated circular dependencies, enforced strict user-scoped memory isolation, and validated system stability under high-concurrency load (10, 25, 50 simultaneous requests).

### Architectural Principles in V1.1
- **User-Centric Tenant Isolation**: Authoritative state is strictly partitioned by `user_id`. No user can read, mutate, link, or delete projects, memories, approvals, or notifications belonging to another user.
- **Relational Ground Truth**: PostgreSQL is the single source of truth for all business state. Redis is strictly an ephemeral acceleration layer (rate limiting, distributed locks, transient cache); losing Redis never destroys authoritative state.
- **Explainable Provenance**: Every injected context item provides verifiable origin tracking and provenance reasoning without exposing internal raw scoring weights to the LLM or user.
- **Strict Human-in-the-Loop Gating**: Side-effecting operations (code execution, git push, force clean, computer control) must route through `SecurityCenter` and cannot bypass human approval.

## 3. Key Features

### 3.1 Personal Context Engine
- Resolves active project context automatically from user intent, linked repositories, or active conversation topics.
- Multi-tier ranking combines vector similarity (cosine metric), importance score (0.0 to 1.0), and time-decay recency (30-day half-life).
- Risk-aware disambiguation: when a risky command ("push it", "delete build") is received and matches multiple workspaces, Kairo prompts for clarification rather than guessing.
- Granular user preference toggles for memory retrieval, project context injection, active git context, and conversation depth.

### 3.2 Project Workspaces
- Workspaces organize work across repositories, workflows, and conversation history.
- Relational schema with cascading integrity across `projects`, `project_repositories`, `project_workflows`, and `project_conversations`.
- Supports primary repository tagging, branch tracking, and project archival.

### 3.3 Unified Command Center UI
- Cohesive single-window interface replacing fragmented tools.
- Command Palette (`Ctrl+K` / `Cmd+K`) for rapid navigation, project switching, and prompt actions.
- Context Inspector drawer displaying real-time active project, token counts, and memory provenance.
- Global Security Banner showing Emergency Stop state, pending approval counts, and active capabilities.
- Fully accessible (WCAG 2.1 AA compliant) keyboard focus traps, ARIA roles, and high-contrast dark theme.

### 3.4 Multi-Agent Orchestration
- `SupervisorAgent` coordinates complex tasks through structured DAG plans with bounded parallelism (max 8 tasks, max delegation depth 1).
- Specialized workers: `ResearcherAgent` (web research & citations), `DeveloperAgent` (sandboxed git & code analysis), `AnalystAgent` (synthesis & diagnosis), `BrowserAgent` (headless web exploration).
- Truth-aware evidence classification strictly separates `OBSERVED` facts, `INFERRED` hypotheses, and `UNKNOWN` variables.

## 4. Security & Safety

### 4.1 Multi-Tenant Authorization
- All memory endpoints (`/api/v1/memory`, `/api/v1/internal/memories`) enforce `user_id` filtering.
- All Project CRUD operations verify user ownership in database query clauses (`WHERE id = :id AND user_id = :user_id`).
- Approvals cannot be decided by non-owner users (`TenantIsolationError`).

### 4.2 Prompt Injection Defense
- Untrusted content (web pages, git diffs, issues, PR comments) is enclosed in `<web_source>` boundaries and sanitized via regex patterns neutralizing jailbreak attempts.
- System prompt instructions strictly instruct the model that reference data cannot modify security policies or authorize actions.

### 4.3 Emergency Stop Switch
- Instantly halts all active side-effecting operations across all agents, tools, and workflows.
- Safe `READ` operations remain available for diagnosis; `WRITE`, `EXECUTE`, and `EXTERNAL` actions are blocked.
- AI models cannot reset the emergency stop; only explicit human operator action can clear the stop state.

### 4.4 Secret Scrubbing & Rejection
- `MemorySanitizer` automatically detects and blocks API keys, server passwords, private SSH/RSA keys, and tokens from entering long-term memory.
- Production origin validation rejects `localhost` and loopback interfaces when `ENVIRONMENT=production`.

## 5. Known Limitations

1. **Computer Control Local Sandbox**: Computer control requires a local graphical desktop environment and is intentionally disabled in cloud/container deployments.
2. **Browser Headless Environment**: `BrowserAgent` requires local Playwright Chromium binaries. In environments without Playwright installed, web research falls back cleanly to the HTTP extraction engine.
3. **OpenRouter Rate Limits**: When operating under free-tier OpenRouter models, high-frequency requests may encounter provider 429 throttling; Kairo's Circuit Breaker and fallback router manage this gracefully.

## 7. Deployment & Operations

### Production Container Deployment
```bash
# 1. Build production image
docker build -t kairo:1.1.0 -f deployment/docker/Dockerfile .

# 2. Run migrations
docker run --rm --env-file .env.production kairo:1.1.0 alembic upgrade head

# 3. Start services via Docker Compose
docker compose -f deployment/docker/docker-compose.prod.yml up -d
```

### Health Verification
```bash
# Liveness probe
curl -f http://localhost:8000/health/live

# Readiness probe (verifies DB + Redis connectivity)
curl -f http://localhost:8000/health/ready
```

## 8. Rollback Procedure

If a critical failure occurs during deployment:
1. **Rollback Container**: Revert container image tag to `kairo:1.0.0`.
2. **Downgrade Database Schema**:
   ```bash
   docker run --rm --env-file .env.production kairo:1.1.0 alembic downgrade 0005_v1_tables
   ```
3. **Flush Ephemeral Cache**:
   ```bash
   redis-cli -u $REDIS_URL FLUSHDB
   ```
4. **Verify Health**: Confirm `/health/ready` returns HTTP 200.
